# Versioned JSON error contract (candidate)

New commands use schema version `1.0`, `{ok:true,...}` on success and `{schema_version:"1.0",ok:false,error:{code,message,retryable,action_required,job_id,account_profile,details_redacted}}` on `RunnerError` failures with `--json`. The error message is intentionally generic in JSON to avoid disclosing secrets from subprocess diagnostics. Explicit error prefixes cover `INVALID_SPEC`, `UNAUTHORIZED_ACCOUNT`, `SOURCE_REVISION_MISMATCH`, `INVALID_DEPENDENCY`, `CONCURRENT_SLOT_EXHAUSTED`, `SUBMISSION_CONFLICT`, `APPROVAL_REQUIRED`, `ACCOUNT_PREFLIGHT_BLOCKED`, `CREDENTIAL_MISSING`, `CREDENTIAL_OWNER_MISMATCH`, `REMOTE_IDENTITY_MISMATCH`, `INVALID_EXPERIMENT_RESULT`, `INVALID_METRIC`, `MISSING_ARTIFACT`, `ARTIFACT_HASH_MISMATCH`, `INCOMPATIBLE_RESULTS`, `EVIDENCE_CONFLICT`, `UNKNOWN_EXPERIMENT` and `RUNNER_ERROR` fallback. `--json` does not imply the operation succeeded: always check `ok` and process exit code.

**Known candidate gaps:** The legacy command success JSON shapes are deliberately preserved for compatibility. Some argparse validation and Kaggle-specific failure classification still use generic codes instead of stable provider-specific taxonomies. Do not parse unstructured stderr or assume retryability from generic error messages.
