# Agent-first experiment workflow (candidate)

The agent should execute `VALIDATE -> PACKAGE INSPECT -> ACCOUNT AUTHORIZATION -> REMOTE PREFLIGHT -> ATOMIC LOCAL RESERVATION -> SUBMIT ONCE -> REMOTE VERIFY -> MONITOR/RESUME -> FETCH -> RESULT VALIDATION -> AGGREGATION -> REPORT`. Use the versioned `ExperimentSpec`, not shell arguments assembled ad hoc. Always compare `source_sha256` across validation and staging, select only profiles explicitly listed in `authorization.allowed_profiles`, and respect Kaggle platform limits. Never attach local sensitive files, publish private datasets, rotate tokens, archive or cancel runs automatically.

The attempt is immutable. `experiment_id` is the logical research problem; `attempt_id` names a single deliberate execution. `job_id` is deterministic from these two names for the candidate agent interface. `kernel_ref` identifies a real Kaggle kernel; a local ID does not prove the kernel exists. `fingerprint` includes spec/source and selected authorized account identity but never credentials. The agent may resume the old attempt after crashes. A repeated `submit` returns the persisted attempt state without another push.

**Operator stop conditions:** missing credential/owner, authorization mismatch, quota or slot exhaustion, ambiguous submission, 403/404 unknown remote state, source-hash change, schema mismatch, private-data concerns or scientific invalidity. Never infer positive scientific results from Kaggle `COMPLETE`.

**Candidate limitations:** This patch introduces agent-specific durable submission but has not migrated the legacy `kgr run` path to atomic reservations. Consequently all agents should use `kgr experiment` exclusively; legacy `run` remains a compatibility interface requiring manual concurrency discipline. Full P0 qualification requires running the existing test suite on the actual repository and verifying CI integration, real CPU/notebook Kaggle runs and any remaining provider-specific edge cases.
